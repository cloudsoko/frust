# WO-043: Email Batteries (notifications as metadata, delivery as a contained side-effect)

> [!info] PM work order — the first "battery" of M4's turnkey half, after the Frust UI re-skin (WO-042) closed the visual half. An ERP that can't email an approval isn't turnkey. Governing: [[Topcoat]] (the in-tree `topcoat-mail` prototype #216) · [[ADR-010 Rollup Ladder]] (the background-worker posture email must match) · WO-024/025 (the kernel's tokio-free design email must not breach) · [[ADR-006 Wire Protocol]] (behavior = metadata).

## The head-start (grounded 2026-07-30)

`topcoat-mail` is a real, well-shaped crate already in the vendored tree:
- `Mail` / `Mailbox` / `Attachment`; a `Transport` trait with **`SmtpTransport`** (lettre, behind the `smtp` Cargo feature) and **`FileTransport`** (writes to disk — the dev/test transport); `MailConfig` + builder; `async fn send(cx, mail) -> Result<Receipt>`.
- So delivery machinery exists. This WO **wires it in**, it does not build a mail library.

## The two constraints that shape the whole WO

1. **The kernel is deliberately tokio-free** (std::thread OS-pool + blocking `ureq`, WO-024/025). `topcoat-mail`'s SMTP transport is **async** (lettre/tokio1). Email delivery therefore must be a **contained background worker** that owns its own async runtime (or uses a blocking transport) — it must NOT drag tokio into the kernel's request path, and a slow/dead SMTP server must NOT block or slow a document save. This is the same posture as the ADR-010 Tier-2 rollup workers and the OOB ticker: lifecycle event → enqueue → background worker delivers.
2. **Behavior is metadata** (the Frust dogfood claim). Adding a notification must NOT require a recompile — it is a kernel-owned rule (a Notification-style DocType: `{trigger doctype + event/condition → template → recipients}`), evaluated by the running kernel. This is Frappe's "Notification" DocType parity, done the Frust way.

## Exit Criteria

1. **Email is metadata, not code** — a kernel-owned Notification rule (write-closed DocType, the rollups/app-registry pattern) defines trigger (doctype + lifecycle event + optional condition), template, and recipients; the running kernel evaluates it and enqueues a send. Prove: a new notification added through the running kernel fires with **no recompile**.
2. **Delivery is a contained background side-effect** — a dedicated mail worker (its own async runtime or a blocking transport) drains an enqueue, isolated from request workers. Measure: a document save with a notification attached does **not** pay SMTP latency on the request path (compare save latency with the mail worker healthy vs. with a dead/slow transport — the save floor must not move), and the kernel's tokio-free request path is unchanged (footprint/throughput held, WO-024/025 numbers).
3. **Dev/test uses `FileTransport`, SMTP is config-selected** — CI captures the rendered message from disk and asserts recipients/subject/body/attachment; no real SMTP server in the suite. Production SMTP is selected by **config, not code** (the tenancy-strategy pattern: `FRUST_MAIL=file|smtp` + connection config).
4. **Failure is contained, observable, and never silent** — a failed send (SMTP down) does not lose the document mutation and does not block the request; it is a bounded retry / dead-letter with a **typed error surfaced in `/metrics`** (silent-slow is the enemy applies to delivery: a notification that silently never sends is the failure mode to design against). No infinite retry loop.
5. **Prove it live through `frust serve` / the browser** (tested-seam≠wired) — a REAL workflow transition on the seeded app (e.g. `sales_invoice` → Submitted → notify the approver) emits a REAL mail captured by `FileTransport`, driven through the running kernel, not a constructed unit test. Assert the message CONTENT, not merely that send() returned Ok (assert-the-outcome).

## Boundaries

- **Never on the hot path.** A slow SMTP server slows email, never a save. Same posture as Tier-2 rollups / the OOB ticker.
- **No second async runtime in the kernel core.** The mail worker's runtime (if any) is an isolated island; the request path stays std-threads + blocking. If containment forces tokio into the core, that's an escalation (below), not a quiet acceptance.
- **No new heavy dependency** beyond `topcoat-mail`/lettre (already in-tree). No second template engine — reuse the Desk's metadata/rendering for templates where practical; a notification template is text/HTML with field interpolation, not a new language.
- **Print/PDF is OUT of scope** — it has no head-start and is its own building-block spike (which HTML→PDF path, respecting the no-heavy-dependency posture) → ADR → WO. PDF *attachments* to email therefore wait on that WO; v1 email attaches the record as HTML/data if an attachment is wanted at all.
- **Decimal/money in templates** — if a notification interpolates a money field, it renders the stored decimal string (compare-never-compute, ADR-007); no arithmetic in a template.

## Escalation

If `topcoat-mail`'s async transport cannot be contained without dragging tokio into the kernel's request path (breaching the WO-024/025 tokio-free posture), STOP and report — it is an architecture decision: a bounded async island for the mail worker vs. lettre's blocking transport. Report the trade with a number (footprint/latency of each), don't pick silently.
