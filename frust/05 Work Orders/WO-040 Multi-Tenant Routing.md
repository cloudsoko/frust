# WO-040: Multi-Tenant Routing (One Process, N Tenants)

> [!info] PM work order — the full tenancy build the [[2026-07-28 WO-039 multi-db tenancy probe]] scoped. **No ADR-003 amendment** (the probe cleared it). The reframe that shrinks this WO: **a tenant already IS a database** (`Db::tenant()` = `cfg.db`); ADR-003's model is the data model. What's unbuilt is only **routing** — today one process holds one `Db`, so multi-tenancy means one process per tenant. This wires one process to serve N tenant databases. Governing: [[ADR-003 Tenancy Model]], WO-039 (the 5 findings), [[2026-07-26 WO-026 surrealdb write concurrency]] (the caches to per-tenant-key), [[2026-07-27 WO-027 backup restore DR]] (per-tenant restore, now operational).

## Exit Criteria

1. **Routing: one kernel process serves N tenants**, resolving each request to its tenant database. The probe found the JWT already carries `ns`/`db` claims that pin the session — so routing is largely "use the *caller's* database from their credential, not a fixed `cfg.db`." Prove: **two tenants served by ONE process**, and isolation is still DB-enforced (WO-039's strongest-form guarantee holds — assert the *provenance* of returned rows, per the standing security-assertion check, not just status).

2. **Shared engine (WO-039 finding 1): `Broker` `Box<dyn HookDispatch>` → `Arc`.** One wasmtime engine + one ticker serves every tenant (the script pool is already `(tenant, doctype)`-keyed, so this is safe). Per-tenant cost collapses from an engine+thread to kilobytes.

3. **Per-tenant cache keys (WO-039 finding 2):** `SESSION_GEN` / `META_GEN` are process-global → make them per-tenant, so one tenant's logout or metadata sync does **not** cold-start every other tenant's WO-026 caches. Prove with a 2-tenant test: tenant A logs out, tenant B's session cache survives (no re-read storm).

4. **THE FOOTPRINT GUARD — re-measure idle RSS at N tenants (1 / 10 / 50).** P-1.4 (60 MB, killed) is the verdict this build is **most likely to undo**, and it's why WO-039 went first. Idle footprint must stay in the tens-of-MB class and **NOT grow linearly with tenant count** — if it does, findings 1–3 didn't cover it and there's more per-tenant state to share. This is the criterion the escalation clause is built around.

5. **The three M3 numbers preserved** (fresh store, full hygiene set): **124 req/s** throughput (WO-026), **25 ms** submit floor (REQ-6.1.1), **60 MB** idle (P-1.4) — all hold with routing in the request path. A tenancy build that regresses any of them has traded away a measured win; that's a finding, not an acceptable cost.

6. **Per-tenant restore operational:** the WO-027 export/restore path wired for one-tenant-at-a-time (enumerate tenants for whole-instance; restore one leaves others untouched — the P-8.1 unlock the probe proved, now an ops path, not just a test).

7. **Re-score P-8.1:** bounded-by-architecture → killed (or tighter), once per-tenant restore is operational and the footprint guard holds. Cite the numbers.

## RESCOPED 2026-07-28 (Boss ruling) — the seam is a `TenancyStrategy`, not a fixed routing choice

> [!important] This WO now builds the **runtime-selected `TenancyStrategy`** seam per the amended [[ADR-003 Tenancy Model]], not "route to db-per-tenant." *Tenancy is not a feature; tenancy topology is a strategy; resolution is one operation it performs.* The four structural invariants (no direct ns/db selection · no shared-context mutation · resolution consumes trusted identity · monopoly enforced structurally) are in ADR-003 and are this WO's acceptance spine. **Preserved from the done work:** C2 (Arc shared engine) and C4 (footprint guard, `tenantmem.rs`) are tenancy-*boundary*-agnostic — still done, and the footprint guard is the regression tripwire for every chunk below. The earlier tenant-prefixed-token ruling (a/b/c/d) survives *reconciled under invariant 3*: the kernel-minted token prefix is the entry point carrying a **canonical `TenantId`**, which the strategy resolves to a `ResolvedTenant` via the registry — never a raw client string substituted into a db name.

**Rescoped chunks (supersede the A–D below):**

- **Chunk A — THE MONOPOLY SEAM [DONE 2026-07-29 — [[2026-07-29 WO-040 chunk A tenancy seam]]].** Introduce `TenancyStrategy` + typed `ResolvedTenant` (crate-private constructor). - **Chunk B2 — PER-REQUEST ROUTING (one process, N tenants) [inserted 2026-07-29, PM — the gap the builder surfaced].** The WO's own title, and it belongs to no chunk yet: Chunk A built the seam (one tenant through it), Chunk B proved two strategies (one tenant each), but *nowhere* does one process resolve each request's tenant from its token and route to that tenant's `scoped_db`. `main` today resolves ONE tenant at boot (`Tenancy::sole()`) and refuses a roster > 1 (honestly enforced, not hidden). ## ~~Continuation sequencing~~ (SUPERSEDED by the rescope above — kept for history)

> [!important] PM ruling (2026-07-28) — the routing mechanism (the probe's "route by JWT claim" framing didn't survive the kernel's opaque-token model): **tenant-prefixed opaque token, option (a).** The kernel uses opaque-token → `_frust_session`-row indirection (not the JWT directly), creating a bootstrapping problem: it must know the tenant DB *before* it can resolve the caller. Ruled:
> - **(a) CHOSEN:** `/login` gets a **login-time tenant hint** (subdomain `acme.frust.app` or a tenant field in the login payload — /login has no token yet and must authenticate against a specific tenant's user table), authenticates there, mints `tenant.<random>`. Every authenticated request routes by **splitting the token before any DB call**; the session row + lookup live in the tenant's own DB. Spoofing `tenant_b.<mine>` fails safely (not in B's table → 401). Preserves the **no-shared-surface** property (WO-039's strongest result) AND **instant revocation** (opaque indirection is load-bearing for WO-033; kept, per-tenant). The prefix is the tenant **slug** (subdomain-known), never a guessable id — don't leak customer number/count.
> - **(b) REJECTED:** a control DB of all sessions re-introduces a shared cross-tenant table — the *auth* surface, the highest-value target — undoing the exact guarantee this milestone gains.
> - **(c) subsumed by (a):** explicit-tenant-per-request is safe but changes the whole client contract; (a) needs the hint only at login and rides the token after.
> - **(d) REJECTED implicitly:** using the self-verifying JWT directly would drop instant revocation (needs a blocklist = another shared table).
> - Not an ADR-003 amendment (implementation *under* it — the model is unchanged). **Record the (a)/(b)/(c) reasoning in Chunk A's build log** (WO-008 identity-decision precedent).
