# WO-034: The v2.0 Gate (Milestone 3 Capstone)

> [!info] PM work order — **assessment, not a build** (WO-023 precedent). v1.0 answered *"is it a Frappe replacement?"*; v2.0 answers *"is it deployable, and where isn't it?"*. The scorecard's three rules apply verbatim: no verdict without evidence, bounded is honest, no grade inflation. This WO writes NO product code — anything it finds becomes its own WO.

## The defining criterion: no bounded-by-assumption left

Milestone 3's brief was set by v1.0's own edges — the lone OPEN was unmeasured memory, and concurrency was bounded *only because the serve loop was never load-tested*. The gate's job is to prove those assumptions are gone. **For every one of the 12 current `bounded` verdicts, classify it:**

- **bounded-by-measurement** — a number bounds it (P-8.2's 1.4×). Honest; stays.
- **bounded-by-architecture** — a design trade bounds it (P-8.1's single-DB restore; F1's Desk→kernel poll). Honest; stays, with the trade stated.
- **bounded-by-assumption** — *untested.* **This is what the gate must eliminate.** Either measure it (→ a quick measurement WO), or reclassify it honestly against evidence. A `bounded` verdict with no number and no named trade is the exact thing this gate exists to refuse — the concurrency-was-assumed hole that opened Milestone 3, caught before it can hide in another row.

## Exit Criteria

1. **Every bounded verdict classified** (measurement / architecture / assumption) with its evidence link. The classification table is the gate's core deliverable.
2. **Zero bounded-by-assumption remain** — each is either measured (cite the WO) or reclassified honestly. If the walk finds one that can't be resolved by re-reading existing evidence, that's a finding → its own measurement WO, and the gate does not pass until it's closed. (The gate is allowed to fail here; that's it working.)
3. **The scorecard re-scored** with Milestone 3's numbers, tally stated, every moved verdict linked to the WO that earned it. No verdict moves without a measurement behind it.
4. **The v2.0 verdict paragraph:** is Frust deployable, and where isn't it? — concurrency (124 req/s, DB-bound), memory (60–84 MB), DR (procedure + secure restore, no PITR), the measured bounds that remain. Honest about what "deployable" does and doesn't cover (single-node, single-DB tenancy, no batteries).
5. **Milestone 3 declared complete; Milestone 4 seeded** from the remaining measured/architectural bounds — the honest backlog: multi-DB per-tenant tenancy (P-8.1, ADR-003 amendment), the batteries (print/PDF, email — mail prototype now in-tree), the Desk→kernel streaming endpoint (F1), and whatever else the classification surfaces.

## Boundaries

- No product code. A bound that needs a number gets a measurement WO; the gate names it, doesn't build it.
- Resist grade inflation harder here than anywhere — this is the deployability claim, and its entire value is that it can be trusted. A bound reclassified from assumption to measurement must have the measurement, not a confident sentence.

## Escalations

If the classification finds a `killed` verdict that Milestone 3's own work quietly undermined (the WO-026/P-1.2 pattern — a mechanism reproduced under new load), **downgrade it honestly**, same as P-1.2. The ledger moving down at its own capstone is the strongest proof it can be trusted.
