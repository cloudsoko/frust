## Standing check: assert the OUTCOME you need, not the operation you performed

**A check that returns a plausible number is not a check.** Four instances in one session (2026-07-27), four domains: WO-016 (epsilon in a money check hid the forbidden defect), WO-028 (count-only assertion missed silently-emptied `lines`), WO-027 (`access_ddl()` returned `OK` while remediating *nothing* — `IF NOT EXISTS` no-op; only "does the remedy CLEAR the refusal" caught it), and the WO-027 cleanup itself (`$r[0].result.count` returned array length 1, not the `count` field 8 — a plausible wrong number). The reliable checks compared something that **couldn't be accidentally satisfied** (a table-name list; a forged-token 401; the refusal actually clearing). Assert the state you need to be true, never that the operation ran without error. The failure mode is always green-and-wrong.

**Security-domain instance (WO-039, and the highest-stakes yet): an isolation test must assert the IDENTITY of what came back, never just the operation's status.** The tenant-isolation probe's first run reported "tenant A CAN read tenant B's database" — a fabricated cross-tenant leak, two minutes from the record. The check was `non-200 OR zero-rows`; A's token returned 200 with **A's own row**, so the check conflated "returned data" with "returned B's data." The fix: assert `owner_tenant == A` (whose row), not the HTTP status. In a security test the outcome you need is *provenance*, and the failure mode cuts both ways — a false leak embarrasses, a MISSED leak from the same sloppy assertion is catastrophic.

**Refinement (WO-040 B2): one sample is not a measurement, and a PLAUSIBLE wrong number is more dangerous than an impossible one.** B2's throughput first read 115.8 req/s vs a 124 baseline — *plausible*, reads as "7% cost, acceptable for the feature." Only 5 samples revealed the truth: 115.8/121.7 were cold-store warm-up, the real value converged at 137.1/137.5/137.8 (spread 0.7). An *impossible* number (Chunk B's 3.3 req/s) forces investigation; a *plausible* one invites acceptance — so it writes a false regression into the log as truth, or excuses a real one. Take ≥3 samples of any variance-heavy metric; converge before comparing. Corollary caught the same day: **c=1 throughput carries NO signal at single-sample size** (26.5→43.2→26.7 across chunks, ~60% swing — at one client, throughput = 1/tail-dominated-mean); stop quoting it as a comparison. Prior "tail variance"/"confirmation" c=1 claims were unearned single samples, corrected.

**Refinement (WO-032, the 6th instance and the sharpest): a metric you have never seen fail is not yet a metric — build the failing control.** WO-032's headline metric was "OS threads per subscriber"; it read `0.000` = pass. But it reads `0.000` in the *stalled* build too — tokio never grows its pool for *blocked* tasks, so the number is invariant under the exact failure it was meant to detect. Only running a deliberately-broken **control** (`std::thread::sleep` instead of `tokio::time::sleep`, one line, never-shipped flag) exposed it: the control stalled the whole Desk at 24 subscribers while reading the same `0.000`. The discriminating measures were *streams stalled* and *request timeouts* — the ones the control made fail. **The technique: don't just assert the outcome — prove your check CAN fail by making it fail. A pass you've never seen paired with a matching fail is decorative.** (Also this session: a metric's literal wording can be satisfied by the broken build — "must not pin a thread per subscriber" was true of the stalled build; intent is what the control asserts.)

**Refinement (upstream track, 2026-07-31): before believing an instrument's ZERO, confirm it reads nonzero on a known-good case.** A mis-quoted grep returned 0 for methods demonstrably present in the shipped bundle — trusted, it would have "found" the fix missing and triggered a wrong-headed rebuild. The zero of a check that can fail for its own reasons is not evidence until the check has been shown to read a known positive. Sibling practice rule, learned twice in one session: **mutation-test by inverting the change in place, never by reverting the file** — `git checkout` on an uncommitted file destroys the work along with the mutation.

## Standing check: tested-seam ≠ wired-in-`serve`

**A seam proven in a test-constructed broker is NOT proven until the resident `frust serve` path exercises it.** Three instances, same shape (green tests over a path the shipped product never took): WO-017 (kernel never ran per-DocType scripts — empty WASI), WO-020 (Desk save never worked for clerks — tests write as manager), WO-022 (serve never wired `with_script_source`; WO-018 c5 Desk workflow buttons claimed-but-unbuilt). Every "delivery"/"lifecycle" WO must include a live-through-`frust serve`-or-the-browser proof, not only a broker-level test. The dogfood (WO-022) caught two of these because it drove the real product.

## Conventions

- ADR profile tables are security boundaries — widening = ADR amendment, not config.
- New tech = building-block note (status: evaluating → leaning → adopted) with capability→pain-point map, honest risks, spike exit criteria before any ADR.
- Pin everything (SurrealDB, Topcoat rev, wasmtime); upgrades are deliberate events.
