## The fifth breaking change the review couldn't see

The WO-025 review was right that all four *named* breaking changes were already
ours from the 2026-07-25 pin-to-main. But the merge surfaced a fifth:

```
- mod content; pub use content::*;
+ pub mod content;
```

Upstream namespaced the content types. `Form`, `Js`, and `Wasm` moved from
`router::*` to `router::content::`, and `frust-desk` failed to compile:
`no Js in router`, `no Wasm in router`, `no Form in router` — note **`Form` is
upstream's own type**, so this wasn't about our patches.

Adapted the Desk's import rather than carrying a patch to undo the namespacing —
fighting an upstream API decision is exactly the drift the vendor discipline
exists to prevent.

**The durable lesson:** "we already absorbed the breaking changes" can only ever
mean "the ones upstream labelled as breaking." A namespacing change is
API-breaking for a downstream that glob-imports, whether or not the changelog
says so. The merge is the probe that finds the unlabelled ones — you do not get
to know the full breaking-change set from reading release notes.

## Retiring the two redundant patches — verified as supersets, not assumed

Upstream merged our owned-string render-hang fix (`c8fb66f`/#201) and our signal

## The narrowing that bit back — and my own error catching it

Upstream's #214 typed `push_str` as `&StrSurrogate`. I asserted no call site
used the wider `impl Deref` form and took upstream's signature. **That assertion
was wrong**, and the suite proved it:

```
error[E0308]: expected `&StrSurrogate`, found `StringSurrogate`
  --> signal_methods.rs:38  message.push_str(e.target.value)
```

`e.target.value` yields an **owned** `StringSurrogate`; upstream's `&`-ref
signature rejects the exact call the method exists for. My "no call site uses
it" came from a `grep | head -20` that truncated before the one file that
mattered.

So `push_str` becomes a **new carried patch** — restored to `impl
Deref<Target = StrSurrogate>`, which accepts both owned and borrowed. This is
the honest cost of adopting #214: it merged one of our patches and narrowed our
API in the same PR.

This is the *fifth* instance this session of the standing check —
**"a check that returns a plausible number is not a check"** — and again I made
it right after the pattern was named. `grep | head` gave a plausible empty
result; the thing that actually held was `signal_methods.rs`, a test that
**can't be accidentally satisfied**. The regression test is the check; my grep
was a proxy for it.

## The built-artifact trap

`browser/dist/index.js` conflicted. Taking upstream's resolved it cleanly — and
**silently dropped our Decimal surrogate from the browser bundle**, while the
Rust side still exposed `Decimal` in expressions. A compiled artifact resolved
by `--theirs` is a merge that looks done and isn't: it was built from a tree
that never had our source.

Rebuilt `dist` from the merged sources (`pnpm build`, per the machine-wide npm
breakage) → **Decimal back in the 19 KB bundle, browser suite 11/11 green.**
Recorded in the ledger as a standing post-merge step: *rebuild dist or the two
languages disagree.*

## Off-order finding (flagged, not fixed)

Every **healthy** kernel boot now logs one `lvl:error / E_DB` line. Traced to
`db.rs:100` (`span.err(e)` — *"failures ALWAYS emit — silent is the enemy"*)
firing on the WO-027 keyguard's deliberately-failing forged-token probe: the
guard's healthy path **is** a refused call, so the "silent is the enemy" rule
dutifully logs the success-of-a-failure at error level. Harmless but misleading
— an operator grepping for `lvl:error` on boot will find one every time. A
one-line fix (the keyguard probe should log its expected-refusal at debug, or
carry a "probe" marker the span honours), but it is WO-027 surface, not WO-029's.
Recorded for the DR/observability backlog.
