# ADR-016 (proposed): Frontend Posture — Headless Kernel + One SSR Desk, App-Building Tier Named Not Silent

## The fork this closes

Raised by the Boss 2026-07-30: Frappe's selling punch is low-code + DocTypes, *completed* by frappe-ui (components, theme, responsiveness, `createResource` data flow). Frust has no equivalent app-building frontend tier — and until now that was decided by omission, WO by WO, never ratified.

## Proposed decision

1. **Frust is a headless metadata kernel + one excellent SSR Desk.** Stated, not implied. No SRS requirement demands an app-building toolkit (verified: the frontend MUSTs are perf floors and Desk-shaped); none of the 34 founding pains is "can't build bespoke SPAs"; and every deep bet in the vault — stack collapse, ADR-004 headlessness, ADR-001 one-dialect SSR, WO-042's zero-script pages — is a bet *against* the second client-side stack that made frappe-ui powerful and gave Frappe its heterogeneity pain.
2. **BYO-frontend is a first-class supported story TODAY — with its cost priced, not hand-waved.** "Supported" converts the REST surface from implementation detail into **a product with compatibility obligations**. Scope of the obligation (proposed): the *documented* REST surface, under the **ADR-006 evolution-policy shape applied to REST** — additive-only growth, breaking changes = versioned majors with deprecation notice. Not a frozen API. Said with a straight face: running Vue frappe-ui against Frust's REST surface is a supported pattern — that's ADR-004 cashing out, not a consolation prize.
3. **The SSR-native app-building kit is a NAMED future milestone (M5 candidate), not a silent absence.** If pulled, it's built from proven primitives — `fui_*` tokens/components, shards, per-field signals, SSE, the six-verb bridge — one stack, no client/server dialect split: the differentiated version of frappe-ui, the thing Frappe wishes it had. A Vue clone is the one option the vision forbids (re-imports the exact stack-split pain) and the only option built from behind.
4. **M5's timing is explicitly coupled to topcoat #275** (opened 2026-07-31, verified: *"compile client code from real Rust to JavaScript instead of runtime expressions — working spike + benchmarks"*). If it lands, the interaction ceiling that motivates the kit **partly dissolves** and the kit's design space changes. That's a decision on someone else's schedule — named here so it's watched, not discovered.
5. **The Research-Index "stack heterogeneity → solved" row is reframed as a trade** (done in this pass): Frust *sidestepped* the pain by not offering the capability that caused it; this note is where the trade is priced.

## Sequencing

**After ADR-015 (extension model).** An app-building tier without a settled extension model builds the showroom before the chassis is final — what a bespoke frontend can do depends on what an app can compose.

## Frontend North-Star (recorded 2026-08-01, Boss vision — direction, NOT yet a build)

Headless kernel + opt-in SSR Desk stands (the decision above). Two Boss visions recorded as the frontend north-star, gated on Frust maturing first (WO-056: the app is **early-alpha** — usable-app before a second renderer):

**1. Frust UI = a design system with RENDERER BINDINGS (why frust-ui is a separate repo — foresight).** The design language (tokens + component vocabulary + API contract) is portable; the renderer *implementations* are not (a Topcoat `view!` component ≠ a Dioxus RSX component). Bindings: **Topcoat-SSR = the Desk today; Dioxus = native desktop/mobile/rich-web later.** Native is where Dioxus earns it — SSR *can't* do native — so Dioxus is **complementary to the Desk, not a replacement** (SSR admin web + native apps, each on its home turf). Payoff: completes **one language end-to-end** — kernel (Rust) + Desk (Rust) + native (Rust/Dioxus) + sandbox (Rust/wasm) — which Frappe (Python+JS, no native) structurally cannot match. It's the BYO-frontend story realized first-party: a Dioxus app is a REST client, subject to the same permission compiler (the alpha holds for free). **Gate:** Frust usable-first + Dioxus mature + a real native need; two renderers is real ongoing cost, justified only if native is a genuine product goal.

**2. Per-tenant RUNTIME UI customization — bounded tokens, NEVER arbitrary code.** Each tenant customizes brand/design-tokens at runtime via a settings singleton — **[[WO-061 Single DocType]] is the vehicle** (a "Brand/UI Settings" record of typed token fields). The Desk (already token-based from WO-037: `--fui-*` CSS variables) loads the tenant's tokens and injects them → white-label per tenant, **no recompile, customization-is-data** (the metadata thesis applied to UI). **Discipline: a bounded, typed token vocabulary (colors/fonts/spacing/radius/logo), NOT arbitrary CSS/HTML/JS** — the alpha instinct (bounded data, not arbitrary code) applied to theming; arbitrary-CSS is an injection surface + a maintenance sink, and bounded tokens render identically across the Topcoat and future Dioxus bindings. **This slice is achievable near-term on the SSR Desk** and pairs directly with the Single DocType build.

**The convergence — CORRECTED 2026-08-01 by [shadcn-html.com](https://shadcn-html.com/) (verified: semantic HTML + CSS design-tokens + web-platform primitives `<dialog>`/`<details>` + vanilla JS only-when-needed, zero deps, framework-agnostic — the *same* philosophy as WO-042's Desk).** My earlier claim "shadcn-level richness needs a client renderer (Dioxus)" was WRONG: shadcn-html gets shadcn-quality components — including the focus-trap dialogs/dropdowns that were Topcoat's WO-042 **behavior ceiling** — from HTML + tokens + web-primitives + minimal PE JS, NO framework, solved exactly as WO-042 already ruled (native `<dialog>` + a one-liner). So **richness is DECOUPLED from Dioxus:**
> - **Richness = near-term, on the SSR Desk you already have** — adopt shadcn-html's tokens + semantic markup + web-primitive behavior into Topcoat `view!` components (inside ADR-004 + the existing `--fui-*` foundation). This is the "surpass frappe-ui richness" half, achievable now, no second runtime.
> - **Dioxus = purely the NATIVE-targets bet** (desktop/mobile), not richness. Gated on Frust maturing.
> - **The precise Topcoat↔Dioxus sharing mechanism (not a code transform):** make a **shadcn-html-style design system the single source of truth** — tokens shared *verbatim*; the semantic-HTML markup is the spec each renderer emits (`view!` server-side, `rsx!` in Dioxus — a codegen from the HTML spec → both macros is the real "transform," HTML-spec as pivot); **web-primitive behavior JS is shared** (it's just DOM, works under either renderer); only the **data-reactivity** layer (Topcoat signals/shards vs Dioxus hooks) is re-authored per renderer. This makes a future Dioxus binding *cheap*.
>
> Do NOT hand-rebuild shadcn component-by-component from scratch (adopt shadcn-html's patterns), and do NOT let a UI ambition grow bigger than the kernel it serves. → building-block notes (`Frust UI`, `Dioxus`) + a Desk-adopt-shadcn-html WO near-term; the Dioxus binding a spike when the native gate opens.
